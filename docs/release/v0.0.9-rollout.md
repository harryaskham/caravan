# Cara v0.0.9 release and canonical Cacophony rollout

Release and rollout receipt for `bd-e741b9`. v0.0.9 carries the join/admission-intent
precedence fix that unwedges the canonical Cacophony queue: priority/FIFO binds
**automatic** selection only, while an explicit `--pr` admission intent proceeds
on its own exact eligibility with non-blocking ordering evidence.

Status: the release side is complete and verified (§1–§7). The canonical
deployment itself is a fleet system-package roll-forward and is tracked by
Cacophony `bd-a10775` (§8); `bd-e741b9` stays open until that read-only proof is
terminal.

Everything below is reproducible. Read-only commands are marked as such; nothing
in this document mutates a tag, a release, or the canonical queue.

## 7. Platform publication history

All three required platforms are published. Getting there was not automatic, and
the next release will hit the same shape:

| Target | How it landed |
| --- | --- |
| `x86_64-linux` | tag-triggered job, 2m14s on `caravan-pocket4` |
| `aarch64-linux` | tag-triggered job on `caravan-ms-dev-2`, ~1h50m (Nix `extra-platforms` build under emulation) |
| `aarch64-darwin` | **local backfill** — no runner advertising `aarch64-darwin` is registered on this repository, so job `89790269868` never got an agent and stayed queued even after its assets were published |

When a runner for one platform is down, exhausted, or simply absent, close the
gap from any host advertising that platform:

```
just release-backfill-target v0.0.9 aarch64-darwin
just release-pin-rows v0.0.9 "bd-e741b9 reviewed release binary"
```

The backfill builds the exact tagged source in a detached worktree, packages the
same assets as CI, and uploads them to the existing tag. It never creates,
moves, or force-pushes a tag, and it refuses to replace an already-published
asset whose digest differs — a queued CI job and a local backfill racing for the
same target can no longer silently swap bytes that a downstream pin already
references.

Until every platform is published, `release-pin-rows.sh` exits non-zero without
`--allow-partial`, so an incomplete release cannot be pinned as if it were
complete.

## 8. Deploy and read-only proof

Cara is a rolling **system** dependency for Cacophony: nothing in the Cacophony
repository selects a Cara version, so deployment is a system-package upgrade on
the hosts that run the queue, not a Cacophony source edit.

Where the deployed version actually comes from, verified on `ms-dev-5`:
`cara` resolves to `~/.nix-profile/bin/cara` →
`/nix/store/...-caravan-0.0.8/bin/cara`, a Nix user-environment entry built from
this flake's `packages.<system>.caravan`. The deployed version therefore tracks
whatever Caravan revision the fleet's own Nix configuration locks, and
`cara self-update` correctly refuses to overwrite it
(`self_update_package_managed`: "upgrade Cara through the package manager that
owns this binary"). Rolling the fleet forward means advancing that lock to a
revision at or after `db1ca86` and switching each node; the canonical
queue-sync workflow then picks the new binary up from the runner `PATH`.

1. Advance the fleet's Caravan pin to `v0.0.9` (`db1ca86`) and switch the
   canonical node(s). Do not hand-place a binary beside the managed one.
2. Confirm the runtime the wrapper will actually select:
   ```
   ./scripts/cara-runtime.sh -- --version           # read-only
   ```
   The receipt on stderr must read
   `caco-cara-runtime-receipt source=system binary=<path> version=cara\ 0.0.9 version_probe_rc=0`.
3. Confirm the canonical queue agrees, read-only, and record the exact
   `caco_materialization` block: `source=system`, `version=cara 0.0.9`,
   `version_probe_rc=0`, `binary=<absolute path>`, `min_cara_version=0.0.0`,
   `provider_mutated=false`, plus the `config_fingerprint`.
4. Append the §3 rows to `.cacophony/cara-runtime-pins.tsv` through Cacophony's
   ordinary reviewed lifecycle.

Cacophony `bd-a10775` tracks steps 1–4 with these exact rows and receipts.
