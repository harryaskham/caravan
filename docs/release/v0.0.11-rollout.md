# Cara v0.0.11 release and canonical Cacophony rollout

Release and rollout receipt for `bd-7099e8`. v0.0.11 restores the reviewed
explicit-intent admission behaviour that 0.0.10 partially regressed, and is the
final slice of the serial repair chain `bd-2015d2` (root arming durability) →
`bd-088a4d` (missing required runs) → `bd-7099e8` (explicit intent + release).

Everything below is reproducible. Read-only commands are marked as such; nothing
in this document mutates the canonical queue or a Cacophony PR.

## 1. What regressed, and what 0.0.11 restores

Conclusive read-only A/B from Cacophony, same PR/head/FIFO front and moment,
as reported in `bd-7099e8` and reproduced live for 0.0.10 vs 0.0.11 in §8:

| Cara | `eligible` | `next_action` | `admission_note` | Behaviour |
| --- | --- | --- | --- | --- |
| `0.0.8` | `false` | `reject` | `null` | FIFO applies to explicit `--pr`; queue wedges behind an unadmitted earlier PR |
| reviewed `0.0.9` | `true` | `new` | present | explicit `--pr` proceeds on its own eligibility; FIFO demoted to a non-blocking note |
| `0.0.10` (unreleased) | `false` | `reject` | present | **regression**: emits the explicit-intent note and then applies FIFO anyway |

The 0.0.10 defect is a category error, not a policy change. `bd-afa02d` /
`choice-019f9d34` correctly required *intent* to be resolved before FIFO
canonical-candidate rejection, but the implementation bound the relaxation to
`AdmissionIntent::Join` and treated `AdmissionIntent::New` as a synonym for
"automatic FIFO selection". Explicit owner `new` intent and automatic
new-caravan selection are not the same thing, so `cara check --pr N` on a
first-admission candidate started failing closed again. It independently
reproduced Cacophony generation4 PR2213's initial refusal.

### 1.1 Documented semantics (the question `bd-7099e8` required answering)

**Explicit owner `new` *is* allowed ahead of unrelated unjoined rows, exactly as
explicit `join` is.** Selection and intent are now two separate, typed axes and
are specified separately in `SPEC.md` § *Admission selection versus admission
intent*:

| Axis | Values | Ordering rule |
| --- | --- | --- |
| `selection` | `automatic` | priority/FIFO binds it for **both** intents, without exception |
| | `explicit` | one exact remote PR named by an owner (`cara check --pr N`, with or without `--tail-pr`/`--head-pr`); admitted on its own eligibility for **both** intents |
| | `checked_out` | the owner's own PR (local `cara check`, every membership operation incl. `renew`/`rejoin`); canonical position is evidence only, exactly as in 0.0.8–0.0.10 |
| `intent` | `new`, `join` | never by itself decides whether order may be relaxed |

`explicit` selection may pass an earlier ordered row **only** while every
bypassed row is an unrelated, unjoined first-admission attempt. It still fails
closed on a joined row (`blocked_joined`), a PR on the candidate's exact base
chain (`blocked_dependency`), a rank-indeterminate row
(`blocked_rank_indeterminate`), a candidate that is not itself a current ordered
admission attempt, and an unresolved/ambiguous join target. Ordering never
substitutes for compatibility, freshness, generation integrity, policy, or
provider success.

The CLI note, the typed decision, and the mutation gate cannot disagree, because
all three are derived from one `AdmissionIntentDecision`:

* `CheckOutput::admission_note` is formatted from `admission_intent.reason`;
* the receipt's ordering problem is gated on
  `admission_intent.order_permits_admission()`;
* `membership` binds the same decision into the durable control-label audit
  (`selection=… intent=… order=… <reason>`) and records
  `provider_mutated`/`idempotent` on it after execution.

`cara next-candidate` now also publishes the matching `automatic_selection`
decision, so the automatic and explicit surfaces can be A/B'd from JSON alone
without inferring anything.

## 2. Product changes

| Path | Change |
| --- | --- |
| `src/admission.rs` | new `AdmissionSelection` axis (`automatic`/`explicit`/`checked_out`); `OrderedRowDisposition::BlockedNewIntent` → `BlockedAutomaticOrder`; `AdmissionOrderOutcome::JoinAheadOfUnjoined` → `ExplicitAheadOfUnjoined`, plus `OwnerSelected`; `evaluate()` takes the selection |
| `src/read.rs` | `check_analysis` passes `explicit` for remote `--pr` and `checked_out` for the current branch; ordering problem gated on `order_permits_admission()`; `admission_note` derived from the decision; `NextCandidateOutput::automatic_selection` added |
| `src/membership/policy.rs` | membership preflight is `checked_out` owner selection |
| `src/membership.rs` | durable audit basis records `selection=` as well as intent/outcome/reason |
| `src/main.rs` | human `check` renders `admission selection=… intent=…` and the `note:` line; `next-candidate` renders the automatic decision |
| `README.md`, `SPEC.md`, `src/lib.rs` | contract text rewritten around the two axes |

### 2.1 Backwards compatibility

Additive on the wire except for two enum spellings that only ever existed in
**unreleased** 0.0.10 (`join_ahead_of_unjoined`, `blocked_new_intent`); no
published Cara ever emitted them. `admission_note`, `admission_intent`, and
`automatic_selection` are `Option` with `skip_serializing_if`, so pre-0.0.9
consumers keep parsing `canonical_candidate` unchanged.

## 5. Cutting the tag

The version bump (`Cargo.toml`, `Cargo.lock`, `flake.nix` → `0.0.11`) lands
through the ordinary agent/reintegration lifecycle, exactly as `db1ca86` did for
v0.0.9. That means `scripts/release.sh` cannot be used to cut this tag: it
refuses when the requested version is already current. Use the fail-closed
first-party recipe added with this release, from a clean checkout:

```
just release-tag v0.0.11                    # tags exact canonical GitHub main
just release-tag v0.0.11 <landed-commit>    # or one exact landed commit
```

`release-tag` refuses unless the commit is contained in canonical GitHub main,
all three of `Cargo.toml`/`Cargo.lock`/`flake.nix` at that commit declare
`0.0.11`, the tag exists neither locally nor on true GitHub, and the working
tree is clean. It ignores daemon-mirror `origin`, verifies the peeled GitHub tag
after push, and never moves or force-pushes a tag.

Pushing the tag triggers `.github/workflows/release.yml`, which builds and
publishes all three targets.

| Field | Value |
| --- | --- |
| Tag | `v0.0.11` (annotated) |
| Tagged commit | the landed `release: v0.0.11` commit on `main` — record the exact SHA here from `git rev-parse v0.0.11^{commit}` |
| Product commit | the landed `bd-7099e8` commit directly beneath it |
| Previous release | `v0.0.9` at `db1ca86bbdfd2327bf8158d770f7da609763d05f` |

`0.0.10` was never tagged or published and must never be: it is the regression
this release removes. Do not re-cut, move, or force-push `v0.0.11`; a defect
ships as `v0.0.12`.

## 6. Portable assets, checksums, and downstream pin rows

Assets are the updatable-cli `TendrilStyle` contract produced by
`scripts/package-release.sh` and asserted offline by `tests/release_contract.sh`:

```
cara-0.0.11-<target>.tar.gz     # single member dir cara-0.0.11-<target>/cara
cara-0.0.11-<target>.sha256
```

Required targets: `x86_64-linux`, `aarch64-linux`, `aarch64-darwin`.

`scripts/release-pin-rows.sh` is the **only** supported way to derive downstream
digests. It re-verifies every published `.sha256` against the archive it
actually downloaded, asserts the two-member archive layout, and fails closed
when a platform is unpublished, so a partially published release can never be
pinned as if it were complete:

```
just release-pin-rows v0.0.11 "bd-7099e8 reviewed release binary"   # read-only
```

Fill this table from that command's output, verbatim — do not transcribe digests
by hand:

| Target | Archive sha256 | Binary sha256 |
| --- | --- | --- |
| `x86_64-linux` | _pending `release-pin-rows v0.0.11`_ | _pending_ |
| `aarch64-linux` | _pending_ | _pending_ |
| `aarch64-darwin` | _pending_ | _pending_ |

If a platform's runner is down, exhausted, or absent (v0.0.9 needed a local
`aarch64-darwin` backfill because no Darwin runner is registered), close the gap
from any host advertising that platform, then re-run the pin rows:

```
just release-backfill-target v0.0.11 aarch64-darwin
just release-pin-rows v0.0.11 "bd-7099e8 reviewed release binary"
```

The backfill builds the exact tagged source in a detached worktree, packages the
same assets as CI, uploads them to the existing tag, and never creates, moves,
or force-pushes a tag.

## 7. Cacophony rollout

Cara is a rolling **system** dependency for Cacophony; no production Cacophony
surface pins a Cara version, and `.caravan/config.yaml` keeps the deliberate
neutral sentinel `min_cara_version: "0.0.0"`. Deployment is therefore a
system-package roll-forward on the hosts that run the queue, not a Cacophony
source edit. That part is unchanged from the v0.0.9 rollout receipt (§8 there).

What `bd-7099e8` specifically owes Cacophony is the **locked flake input**.
Cacophony's `flake.nix`/`flake.lock` carry a `caravan` input used for
developer/validation builds, locked before `1722445` at the time of the v0.0.9
audit. To move it to this release, through Cacophony's own reviewed flake-update
path:

```
# in the Cacophony checkout, after v0.0.11 is published
nix flake lock --update-input caravan       # or pin the exact rev/ref below
```

| Field | Value for the Cacophony `caravan` input |
| --- | --- |
| `type` | `github` |
| `owner` / `repo` | `harryaskham` / `caravan` |
| `ref` | `v0.0.11` |
| `rev` | the tagged commit recorded in §5 |
| `narHash` | whatever `nix flake lock` writes; never hand-edited |

Then append the §6 rows to `.cacophony/cara-runtime-pins.tsv` in the exact
tab-separated format `release-pin-rows.sh` emits
(`version<TAB>binary-sha256<TAB>platform<TAB>archive-sha256<TAB>context`),
including its `# v<version> assets:` and `# archive sha256:` header comments.

Do not update the Cacophony input, the pins file, or the fleet package set until
`just release-pin-rows v0.0.11` exits zero **without** `--allow-partial`.

## 9. Rollback

Known-good previous release is **`cara 0.0.9`**, tag `v0.0.9`, commit
`db1ca86bbdfd2327bf8158d770f7da609763d05f`, whose reviewed digests are recorded
in `docs/release/v0.0.9-rollout.md` §3 and in
`.cacophony/cara-runtime-pins.tsv`. Rollback is a system-package downgrade plus
reverting the Cacophony `caravan` flake input to its previous locked rev; no
other Cacophony source revert is required because nothing else pins a Cara
version.

Rolling back to 0.0.9 is behaviourally safe for the queue: 0.0.9 already admits
explicit `--pr` intent. Rolling back to 0.0.8 — or shipping 0.0.10 — re-wedges
explicit admission behind the FIFO front candidate, which is the defect this
release exists to remove.
